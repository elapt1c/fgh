cipher_ghost wrote:
Anyone else been looking into lattice-based cryptography?

Been running Kyber-1024 in my messaging stack for about 3 months now. Performance hit is noticeable but acceptable — roughly 2.3x slower key generation compared to X25519, but the actual encryption/decryption is surprisingly fast.

My current setup:

Transport: WireGuard + custom PQ handshake
Storage: XChaCha20-Poly1305
Messaging: Signal Protocol + CRYSTALS-Kyber hybrid
DNS: DNSCrypt with ODoH fallback

The hybrid approach is key right now. Don't drop your classical crypto — layer PQ on top of it. If the PQ stuff breaks, you still have your proven algorithms as fallback.

I wrote a Python wrapper for the liboqs library that makes it pretty easy to experiment with PQ algorithms:

from pq_wrapper import KeyExchange, Encrypt

# Kyber key exchange
kex = KeyExchange('kyber1024')
public_key, secret_key = kex.generate_keypair()
ciphertext, shared_secret = kex.encapsulate(public_key)

# Hybrid encryption
enc = Encrypt('aes256gcm+kyber1024')
encrypted = enc.seal(plaintext, recipient_pk)
decrypted = enc.open(encrypted, secret_key)

Will open source it once I clean up the API. The goal is to make PQ crypto as easy to use as nacl or cryptography.io.

One thing I noticed — Kyber key sizes are significantly larger. We're talking ~1.5KB for public keys vs 32 bytes for X25519. Something to think about for constrained environments.

Great thread. Let me add the zero-knowledge perspective here.

We've been using ZK-SNARKs for authentication in our latest project. The idea is simple: prove you know the password without ever transmitting it. Combined with PQ crypto for the transport layer, it's pretty robust.

Current ZK stack:

Proof System: Groth16 (moving to PLONK)
Curve: BN254 (PQ-vulnerable, I know)
Circuit Compiler: Circom 2.0
Verifier: On-chain (Ethereum L2)

The elephant in the room is that most ZK systems rely on elliptic curves that are quantum-vulnerable. There's active research on lattice-based ZK proofs but they're not production-ready yet.
